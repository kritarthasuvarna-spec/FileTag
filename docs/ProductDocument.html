🏷 FootNote

Attach a personal note to any file on your PC — stored invisibly with the file itself, carried through renames and moves, and synced across machines when the file lives in a Google Drive or OneDrive folder.

Windows 10 / 11 C# · .NET 8 · WPF No database No admin rights No cloud APIs $0 to build & ship

1Product overview

Every file system remembers what a file is — none remembers why you kept it. FootNote answers that question in place: select a file, press a hotkey, type a note. Click the file weeks later and the note slides up from the edge of the screen. There is no app window to open, no database to maintain, and nothing for other programs to trip over.

Design principles

The note lives with the file

Notes are stored in the file's own NTFS alternate data stream, or in a hidden companion file where streams can't survive. No central store means no orphaned records and no re-linking logic — a rename or move simply carries the note along.

Invisible until it has something to say

Files without notes never trigger anything. The overlay bar appears only when a selected file actually has a note, and the hotkey is the only way a first note gets created.

The file is never touched

Content, size as apps see it, and the modified timestamp are all preserved — FootNote captures and restores file times around every stream write. Every application opens the file exactly as before.

Leaves nothing behind

Uninstall strips every note FootNote ever created, from both storage backends, and removes all registry entries and local data. No orphaned hidden data with no app left to manage it.

Cross-device by riding existing sync

Inside Google Drive Desktop or OneDrive folders, notes are written as small hidden files the sync engine uploads like anything else — so a note tagged on PC A appears on PC B. No accounts, no provider APIs, no internet dependency.

Nothing is silently overwritten

Both backends store a capped 20-entry version history rather than a single string. Sync conflicts and accidental edits are recoverable, not lossy.

Competitive position

Windows does ship a native "Comments" field (file Properties → Details), and FootNote was checked against it deliberately. The overlap is thin: the native field only exists for file types with a writable property handler (Office documents, some images and media) — plain text, PDFs, code, and arbitrary files can't be commented at all. Where it does work, it modifies the file itself (changing hashes and modified dates), is buried three dialogs deep, and displays nothing contextually. FootNote works on any file, never touches the file's content or timestamps, shows the note the moment the file is clicked, and syncs it across machines.

What FootNote deliberately is not

  • Not a shell extension. No COM registration, no context-menu handler, no icon overlays — the historically fragile approach was rejected at design time. Detection is done with UI Automation from a normal user process.
  • Not a tagging database. The local index is a lookup cache only — rebuildable, never the source of truth.
  • Not a cloud service. The only network call the app ever makes is an optional version check against GitHub Releases.

2The core interaction

Two paths, one UI — everything routes through the bottom (or top) overlay bar:

  1. Passive display. Click a file in Explorer or on the desktop. If it has a note, the bar slides in showing it — read-only, with Edit and ✕ buttons and the last-edited timestamp. No note → nothing happens, silently.
  2. Active add / edit. Press Shift+Alt+N (default; remappable) with a file selected. The bar opens in edit mode: pre-filled if a note exists, cursor at the end, live character counter capped at 500 (turns red near the limit), Save / Discard, Esc to discard, Ctrl+Enter to save. Saving empty text removes the note.

  • Slides in/out with a ~150 ms eased animation (can be turned off).
  • Docks to the bottom or top work-area edge of the monitor hosting the active Explorer window — or a manually pinned monitor — positioned in raw pixels so per-monitor DPI can't skew it.
  • Tracks the active Explorer tab on Windows 11: each tab's shell view is resolved through IShellBrowser and only the visible one is queried, so tab switches behave like window switches.
  • The storage backend in use (stream vs. companion file) is completely invisible — the bar behaves identically either way.

3Feature reference

Hotkey resolution chain — never a dead key

When the hotkey fires, FootNote resolves "which file do you mean?" through a strict fallback chain, so the shortcut always does something useful from anywhere in Windows:

#SourceDetail
1Explorer selectionThe single selected file in the foreground Explorer window (active tab on Win11), resolved via Shell automation
2Desktop selectionThe selected desktop icon, resolved through the desktop's shell view (IShellWindows.FindWindowSW) — works even with OneDrive-redirected desktops

Multi-selection and folders are deliberately ambiguous → a toast, not a guess. FootNote's own companion files (.footnote) can never themselves be commented or surfaced.

Failure feedback — every time, not once

Failures toast on every occurrence (unlike the one-time first-run balloon), but only from an active hotkey attempt or a save — passive browsing never toasts, so scrolling a folder of unsupported files stays silent. Every failure toast also writes a matching ERROR line to the log: the toast disappears in seconds, the log line doesn't.

Everything else

  • Tray icon — the app's only always-visible surface: Settings…, Open logs folder, Start with Windows toggle, Check for updates, Exit.
  • First run — one balloon, shown once ever: "FootNote is running. Select a file and press [hotkey] to add a comment."
  • Relocation notice — launching the exe from a new folder shows "FootNote is running — now installed at …", so a portable launch never looks like a no-op.
  • Update check — on launch, a background query of the GitHub latest-release tag; a newer version produces one quiet balloon linking to the download page. Never auto-installs, never nags, fails silently offline.

4Storage architecture

Notes are stored through one of two interchangeable backends behind a single ICommentStore interface, chosen automatically per file. Nothing above the router knows or cares which backend owns a file.

AdsStore — local NTFS drives

The note lives inside the file as a named alternate data stream: report.xlsx:FootNote.txt. Invisible, zero extra files, and renames/moves within NTFS carry it automatically. File timestamps are captured and restored around every write so the file looks untouched.

SidecarStore — cloud folders & non-NTFS

The note lives in a small hidden companion file: report.xlsx.footnote, same folder. Used where streams don't exist (FAT32/exFAT) or wouldn't survive (cloud sync uploads strip ADS — a plain hidden file uploads fine, which is what makes notes appear on a second PC).

Routing rules

flowchart TD
    A["File path"] --> B{"Inside a known cloud-sync folder?
(Google Drive / OneDrive)"}
    B -- "Yes" --> S["SidecarStore

    B -- "No" --> C{"Drive is NTFS?"}

    C -- "No (FAT32 / exFAT)" --> S

Reads are resilient to moved files: the routed backend is tried first, then the other — so a file dragged from a local folder into OneDrive with its stream still attached remains readable. Saving migrates: the note is written to the correct backend for where the file lives now and the stale copy is removed, history intact. Delete cleans both backends, including orphaned companion files whose original moved away.

Data format — versioned, both backends identical

{
  "history": [
    { "text": "Draft — needs review",                     "at": "2026-07-10T09:12:00Z" },
    { "text": "Final version sent to client on June 12.", "at": "2026-07-14T11:50:00Z" }
  ]
}
  • Capped at 20 entries, oldest dropped first. The UI shows and edits only the latest entry; the format is ready for a "view history" feature with no storage migration.
  • Sync conflicts (same file's note edited offline on two PCs) become two recoverable histories, not silent data loss.
  • Backward compatible reads: legacy v1 single-note JSON and even hand-written plain-text streams parse as a one-entry history and upgrade to the current format on next save.
  • Notes are capped at 500 characters — a sticky note, not a document.

Cloud-sync folder detection

Purely local — no API calls, no accounts, no internet. Detected at startup and refreshed lazily every 15 minutes, never on the hot path of a file click.

ProviderDetection sources
OneDriveEvery account under HKCU\Software\Microsoft\OneDrive\Accounts\* (UserFolder value — Personal, Business1, Business2… never hardcoded), plus the OneDrive / OneDriveConsumer / OneDriveCommercial environment variables
Google Drive DesktopMount points parsed from DriveFS preferences in HKCU\Software\Google\DriveFS, plus a volume-label fallback that finds mounted "Google Drive" drives (streaming or mirror mode)
Honest fragility note
Cloud detection reads undocumented local config, not a public API — Google and Microsoft can change these internals without warning, so this is budgeted as occasional maintenance, not a one-time cost. Every source fails independently and silently: if detection breaks entirely, the router degrades to plain NTFS routing — notes keep working locally, they just lose the cross-device behavior instead of the app crashing.
Collaborator visibility — mitigated, not hidden
Companion files are hidden in your own Explorer but fully visible to anyone else sharing the Drive/OneDrive folder — on the web, on phones, on Macs. So the first note saved into a detected sync root also drops a one-time _FootNote_ReadMe.txt there (only if absent, targeting My Drive on letter-mounted Google Drive since the virtual root isn't writable), turning a confusing stray file into a self-explanatory one.

The local index — cache, never truth

%LOCALAPPDATA%\FootNote\index.json tracks which paths currently carry a note, so future features (search, export, bulk manage) never need a full-drive rescan. It stores paths only, never note text, is fully rebuildable, and can go stale but never wrong — note text always lives in whichever backend owns the file. Its one load-bearing job today: telling the uninstaller which files to clean.

Detection: UI Automation, kept cheap

  • Selection events are subscribed once at the UIA root (from a background MTA thread), so new Explorer windows and Win11 tabs are covered automatically — nothing to re-attach per window.
  • Events fire system-wide on every selection anywhere, so the handler early-exits on process id (explorer.exe only) before doing anything else. A foreground-window WinEvent hook catches window/tab switches and closes.
  • Bursts collapse into one evaluation ~120 ms after the burst ends; the existence check (File.Exists on the stream or sidecar path) gates whether the bar shows at all.
  • Full file paths come from Shell automation (Shell.Application in-process — this is not a shell extension and registers nothing), with active-tab resolution via each view's IShellBrowser window handle.

Logging

One shared Logger in Core, used by Setup, the app, and Uninstall alike — plain text that opens in Notepad, format timestamp | LEVEL | component | message, levels INFO / WARN / ERROR. The app log rolls daily (or at 5 MB) and keeps ~7 days. Tray → Open logs folder jumps straight there. Logging can never throw into the code it observes.

6Install & distribution

Distributed free via GitHub Releases in two forms. Everything is per-user: no admin prompt, ever.

FootNote-Setup.exe — the recommended path

A small custom WPF installer in the app's own design language, not an off-the-shelf wizard. Five screens: Welcome → Install location (default %LOCALAPPDATA%\FootNote, Browse to change) → Options (launch on startup ✓, launch after install ✓) → Progress → Finish (with an "Open Settings" button). Progress shows four real steps, each reported only when its work actually completed and each logged to install.log: copying files → registering startup → detecting cloud folders → writing the Apps & Features entry.

Portable zip

Extract anywhere, run FootNote.App.exe. The app self-registers on every launch — startup entry (honoring the user's toggle) and the Apps & Features entry — and re-points both automatically if the folder moves. Zip and Setup produce identical registration.

Updates

No store means no auto-update: the app quietly checks the GitHub latest-release tag at launch and shows one balloon if newer. Updating is: exit → extract new zip over the folder (or run the new Setup) → done. Notes and settings are unaffected by updates.

Uninstall — a wizard, never silent

Uninstall is destructive by deliberate decision — it strips every note FootNote created — so it is never one-click. Confirm states the real number: "delete comments from N tagged files", pulled live from the index. Progress counts through "Removing comment 14 of 42…". Finish summarizes removed vs. skipped with a link to the log.

  1. Strip every indexed note via its backend — stream or sidecar; the files themselves untouched. Moved/deleted files are skipped and logged, not failures. Orphaned sidecars are cleaned even when the original file is gone.
  2. Stop the running tray process.
  3. Remove the startup entry and the Apps & Features key.
  4. Delete local data (index, settings, logs).
  5. Delete the install folder — scheduled to run after the process exits, since the uninstaller lives inside it. The uninstall log is written to %TEMP%, never the install folder: a log inside the folder being deleted would erase its own record.
Engineering note — reinstall race guard
The scheduled folder deletion is authorized by a sentinel file. Launching FootNote — or running Setup — into that folder removes the sentinel, cancelling a still-pending deletion instead of letting it eat the freshly installed files. A normal uninstall with no reinstall still cleans up completely.
Engineering note — wizard without the weight
Uninstall.exe (what Apps & Features invokes) is a 12 MB stub that launches FootNote.App.exe --uninstall, which hosts the wizard UI. A standalone WPF uninstaller would have shipped a second ~80 MB runtime for three screens.

8Security & privacy

  • Runs entirely as the user. asInvoker manifest; no elevation path exists anywhere in install, use, or uninstall.
  • One outbound call, ever: the optional update check to the GitHub Releases API. No telemetry, no accounts, no cloud-provider APIs. Cloud-folder detection reads local env vars and HKCU registry only.
  • Note text never leaves the file's location. The index stores paths only; logs record paths and events, not note contents.
  • ADS heuristics tested up front. Because alternate data streams have a malware history, some AV/EDR tools flag writers heuristically. This was treated as a launch risk and tested first: stream writes and all shipped binaries scan clean under Windows Defender.
  • Unsigned binaries (the $0 constraint) — the one real trust friction; SmartScreen warns on first run of a downloaded copy.

10Known limitations

Accepted at design time — documented rather than over-engineered around:

  • Sending a file elsewhere strips the note — email attachment, upload to an untracked web service, non-supported sync products. By design, not a bug to chase.
  • True cloud-only files (never synced locally, web-only) aren't reachable — sidecar storage requires a local synced folder to exist.
  • Companion files are visible to shared-folder collaborators — hidden only in your own Explorer, not cross-user. Mitigated by the one-time explanatory readme at the sync root, not fully solved.
  • Cloud detection can silently lose cross-device behavior if Google/Microsoft change their local config formats — degrades to local-only notes, never crashes.
  • Renaming a file in a cloud/USB folder orphans its companion note. ADS follows renames; a sidecar can't. The note isn't lost — it's still there under the old name — but won't display until re-linked manually.
  • Sync conflicts aren't auto-merged. Editing the same file's note offline on two PCs produces two histories that need a manual merge — recoverable thanks to versioning, but not automatic.
  • Shift+Alt is also Windows' input-language switcher when multiple keyboard languages are installed — the default hotkey can flip input language as a side effect. Remap in Settings if it bites.
  • OneDrive "free up space" re-downloads replace the local copy — an ADS note on a file that predates its cloud folder membership doesn't survive that; sidecar-stored notes do.
  • Windows only. No macOS/Linux; both the storage layer and the detection layer are Windows-specific by nature.
  • No icon overlay badge — part of the rejected shell-extension approach.

11Quality & verification

  • Storage suite: 42 automated checks covering both backends — write/read/delete, rename & move survival, host-file timestamp preservation, history capping and ordering, the 500-char cap, legacy-format parsing and upgrade, hidden-sidecar overwrite, ADS→sidecar migration with history intact, orphaned-sidecar cleanup, and index round-trips. Plus a live-probe mode (FootNote.ConsoleTest <path> [text]) that reports routing and saves against real files.
  • Live end-to-end verification on a real machine: passive display and hotkey editing driven through actual Explorer windows and the actual desktop; clipboard and picker fallbacks; settings changes (edge, accent, auto-hide, hotkey remap) confirmed visually taking effect; sidecar notes created through the UI inside a real Google Drive mount.
  • Full lifecycle tested: Setup wizard (silent and interactive) → use → uninstall wizard, with registry, files, logs, and stripped notes verified at each stage — including the uninstall-then-quick-reinstall race.
  • Defender scans clean on ADS writes, the app, the zip, and the Setup exe.
  • Cross-device sync verification (tag on PC A, see it on PC B) requires a second machine and is the one spec test outstanding.

13Roadmap — explicitly deferred

Deferred deliberately; the IndexStore and the versioned storage format exist today specifically so these are cheap to add without re-architecting:

Search across notes

Index-driven; no full-drive rescan needed.

View history UI

The 20-entry history is already stored; only the surface is missing.

Color tags & bulk manager

Categorize and manage notes across many files at once.

CSV / JSON export

Walk the index, emit the histories.

Tier-2 settings

Dark/light theming, floating-panel layout option.

Cloud-provider APIs

OneDrive Graph / Google Drive / Dropbox APIs for files that never touch a local synced folder — a separate milestone, if ever.
